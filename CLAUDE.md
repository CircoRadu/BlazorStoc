# Instrucțiuni pentru Claude

Acest proiect folosește colaborare strict secvențială între Claude și Codex. Claude nu lucrează niciodată simultan cu Codex.

> **Actualizare 25 septembrie 2026 (prevaleaza asupra restului acestui fisier):** Claude este agentul principal si singurul agent activ al proiectului; predarea catre Codex a fost eliminata. `.collaboration/state.json` are `mode: claude_only`, deci `nextAgent` ramane `claude`, iar `agent-cycle.ps1 finish` nu mai preda catre alt agent (nu mai sunt necesare commituri de schimbare a ordinii). Un task ramane un ciclu (`start` ... `finish`) care se incheie cu un commit. Referirile de mai jos la Codex, la predare si la `nextAgent: codex` sunt istorice.
>
> **Actualizare 29 septembrie 2026 (prevaleaza asupra sectiunii "Inainte de predare" de mai jos):** Claude nu mai face commit automat la finalul fiecarui task/ciclu. Dupa implementare, verificari si actualizarea documentatiei (`docs/PROJECT_STATE.md`, `TODO.md`/`IMPLEMENTED.md`, `docs/TESTE_RAMASE.md`, `VALIDARE.md`), Claude se opreste cu modificarile necomise si asteapta o cerere explicita a utilizatorului inainte de a rula `agent-cycle.ps1 finish` sau orice alt `git commit`. Lucrul continua normal intre task-uri fara commit intre ele (working tree-ul poate ramane cu modificari necomise de la un task la altul); verificarea "working tree curat" de la pasul 3 din "Inainte de orice modificare" se relaxeaza in mod corespunzator (modificari proprii, necomise, ale sesiunii curente/anterioare de Claude nu blocheaza inceperea unui task nou, insa nu se sterg si nu se suprascriu fara sa fie intelese intai). Commitul, cand e cerut, poate acoperi mai multe task-uri deodata.

> **Calculator nou sau mediu lipsa (02 octombrie 2026):** daca .NET 9, MariaDB-ul local sau fisierele `local-secrets/*.private.json` lipsesc, nu improviza: urmeaza `docs/SETUP_DEZVOLTARE.md` (scripturile `tools/setup-dev-environment.ps1`, `tools/dev-mariadb.ps1`, `tools/start-preview.ps1`). Inainte de fiecare push se ruleaza `tools/export-dev-data.ps1`.

> **Context redus (07 octombrie 2026, prevaleaza asupra pasilor 1-4 de mai jos):** citeste la inceputul unui task doar `docs/PROJECT_STATE.md` (starea scurta, 2-5 KB) si taskul relevant din `TODO.md`; `docs/HARTA_COD.md` spune unde se afla fiecare modul. `IMPLEMENTED.md`, `docs/AGENT_CHANGELOG.md`, `VALIDARE.md`, `docs/TESTE_RAMASE.md` si `docs/arhiva/` NU se citesc integral: cauti cu `rg -n` dupa titlu si citesti intervalul. Starea Git se ia din `git status --short`, nu dintr-un instantaneu scris. Teste: `tools\run-checks.ps1` (log complet in fisier, in context doar rezumatul). Documentare: `tools\log-task.ps1`. Alte reguli: `..\PROTOCOL_CLAUDE_OPTIMIZAT.md`. `agent-cycle.ps1 start` nu mai cere working tree curat (avertizeaza doar).

## Înainte de orice modificare

1. Citește `docs/SEQUENTIAL_COLLABORATION.md`, `docs/PROJECT_STATE.md`, `TODO.md` și ultimele intrări din `docs/AGENT_CHANGELOG.md`.
2. Rulează `git status --short` și `git log -1 --oneline`.
3. Working tree-ul trebuie să fie curat. Dacă există modificări necomise, nu le elimina și nu începe alt task; urmează procedura de recuperare din protocol.
4. Verifică `.collaboration/state.json`. Claude poate începe doar când `status` este `ready_for_handoff` și `nextAgent` este `claude`, exceptând cazul în care utilizatorul cere explicit schimbarea ordinii.
5. Pornește ciclul cu:

   ```powershell
   .\tools\agent-cycle.ps1 start -Agent claude -Task "descrierea concretă a lucrării"
   ```

## În timpul lucrului

- Respectă prompturile utilizatorului și limitează modificările la taskul activ.
- Nu rescrie și nu anula modificările Codex fără o cerere explicită.
- Păstrează implementarea asincronă, fara integrare NAS in aceasta etapa. Docker este PERMIS (decizia utilizatorului, 30.09.2026) pentru mediul de dezvoltare si testare, in special o instanta MariaDB pentru teste; aplicatia in sine ramane rulabila direct cu .NET, iar publicarea in containere/QNAP ramane in afara fazei curente.
- Nu genera fișiere SQL de upgrade separate; modificările de schemă sunt gestionate în proiect.
- Toate datele calendaristice afișate utilizatorului au forma `dd.mm.yyyy` (de exemplu `25.09.2026`; cu oră: `25.09.2026 14:08`), în orice pagină, dialog, jurnal, mesaj sau document generat. Formatele interne (`yyyy-MM-dd` în SQLite, `dd-MM-yyyy` în coloana existentă `io_data` din MariaDB, adresele URL) nu se afișează; se folosesc `StockMovementRules.DisplayDate` și formatul `dd.MM.yyyy`.
- După modificări funcționale, actualizează preview-ul local la `http://127.0.0.1:5082/`.
- **La terminarea fiecărui task rămâne în funcțiune un preview cu implementarea**, pe care utilizatorul o evaluează; agentul **nu** îl oprește la sfârșitul ciclului (utilizatorul închide instanța manual). Dacă `5082` este ocupat de o instanță veche pe care agentul nu o poate opri, preview-ul se pornește pe alt port liber (de exemplu `5083`) și portul este comunicat utilizatorului la predare.
- **Fisierele `.md` se scriu fara diacritice** (a, i, s, t in loc de ă, â, î, ș, ț), regula data de utilizator la 25 septembrie 2026: se aplica tuturor textelor noi sau modificate din `TODO.md`, `README.md`, `VALIDARE.md`, `docs/*.md` si din cele doua fisiere de instructiuni. Textele afisate utilizatorului de aplicatie (cod, `.razor`, `.cs`) pastreaza diacriticele; citarile lor in documentatie se scriu fara diacritice. Textul deja existent nu se converteste decat la cererea utilizatorului.
- **Jurnalizare detaliata (regula permanenta, data de utilizator la 30 septembrie 2026, valabila si pentru dezvoltarile ulterioare):** fiecare operatie noua care modifica date se jurnalizeaza cu o actiune care descrie exact tipul ei (de exemplu "Modificare expirare ITP", "Mutare echipament"), nu cu "Editare"/"Adaugare" generic; actiunea se adauga in `AuditActions`, in filtrul paginii Audit si in `AuditActions.IsCreateOrEdit` (pentru link catre obiect), iar un test verifica jurnalul. Detaliile contin valoarea veche si noua, iar motivul poate fi generat automat cand interfata nu il cere.
- **Campuri cu etichete `<...>` (regula permanenta, data de utilizator la 02 octombrie 2026):** orice camp de text in care se adauga etichete prin apasarea unor butoane foloseste componenta `Components/Shared/MarkedTextField.razor`: eticheta se insereaza **la pozitia cursorului** (nu la sfarsit), etichetele apar in text intr-o culoare proprie (necunoscutele in rosu) si spatiile din afara lor au simbolul vizibil; nu se foloseste un `textarea` simplu cu adaugare la sfarsit.
- **Elemente alaturate in formulare (regula permanenta, 08 octombrie 2026):** un comutator, buton sau nota care sta pe acelasi rand cu un camp cu eticheta se aliniaza cu caseta campului (CSS comun, ex. `.editor-grid > .row-toggle`) sau se muta pe propriul rand; nu sta „plutind" langa un camp.
- **Fara contur gros la campurile active (regula permanenta, 08 octombrie 2026; include listele derulante):** niciun `input`/`select`/`textarea` activ nu primeste inel exterior (`outline`); evidentierea este bordura verde de 1 px + umbra de 1 px (regula comuna din `wwwroot/app.css`), iar la containere cu chenar propriu (`.search-box`) trece pe container (`:focus-within`). Butoanele si linkurile au inel discret de 2 px la `:focus-visible`. Nu se adauga contururi proprii pe pagini.
- **Continut in card cu margine interioara (regula permanenta, 08 octombrie 2026):** campurile, butoanele si notele puse direct intr-un card (`.catalog`) langa antetul lui stau intr-un `<div class="catalog-body">` (padding 24 px) si nu ating niciodata chenarul cardului; tabelele care umplu cardul (`.table-scroll`) raman pe toata latimea.
- **Iconite pe randurile tabelelor (regula permanenta, 08 octombrie 2026):** in orice tabel, actiunile universale de pe un rand — editare/modificare/redenumire si stergere/scoatere/eliminare — sunt butoane doar cu iconita (creion, cos de gunoi), clasa comuna `row-icon edit` / `row-icon delete` din `wwwroot/app.css` (32 px, pictograma SVG desenata din CSS; nu se folosesc glife text precum ✎ sau ×, nici cuvintele „Editeaza"/„Sterge" pe butoane de rand). Fiecare are obligatoriu `aria-label` si `title` cu obiectul vizat (ex. „Editeaza sablonul X"); un buton dezactivat isi explica motivul in `title`. Actiunile specifice domeniului (Stornează, Rezerva, Muta, Istoric, Bon, Reactiveaza) raman butoane cu text, iar butoanele de pagina/formular (in afara tabelelor) raman cu text. O actiune noua de editare/stergere pe un rand foloseste aceste clase, nu un stil propriu.
- **Fara casete de bifat (regula permanenta, data de utilizator la 06 octombrie 2026):** nicio pagina sau componenta noua nu foloseste `input type="checkbox"` / `InputCheckbox` simplu; orice bifare este comutatorul On/Off din `Components/Shared/ToggleSwitch.razor` (aspectul „Activ / Inactiv" din lista de sabloane: `Value`/`ValueChanged` sau `@bind-Value`, `Compact` pentru un comutator pe fiecare rand de tabel fara textul starii, `Mixed` pentru selectia partiala, `OnText`/`OffText` pentru alte cuvinte decat On/Off). Starea partiala nu mai foloseste JS (`checkbox-indeterminate.js` a fost scos). Unde un comutator nu se potriveste se propune o alternativa utilizatorului, nu se revine la caseta de bifat: selectia pe randuri de tabel (inventar, preluare factura) este `Components/Shared/RowSelect.razor` (marcaj rotund cu bifa) + clic oriunde pe rand (`tr.selectable-row`) + „Selecteaza tot" in antet; vizibilitatea straturilor de pe pagina este un buton cu `aria-pressed`.
- **Coloanele de pe overlay (regula permanenta, 06 octombrie 2026):** la crearea unui sablon de factura toate coloanele gasite pe pagina pornesc ca folosite la import (si cele cu antet nerecunoscut, de exemplu „Taxa verde"); utilizatorul sterge sau dezactiveaza ce nu are nevoie.
- **Editarea unui sablon de factura nu trece sablonul prin analiza fisierului:** se afiseaza exact ca salvat peste factura model; analiza porneste numai la cererea utilizatorului (butonul „Analizeaza fisierul"). Parasirea editarii (alt sub-tab, tab sau pagina) o inchide, cu avertizare daca exista modificari nesalvate (`UnsavedChangesTracker`).
- **Etichete cu vocabularul sablonului (regula permanenta, 02 octombrie 2026):** etichetele campurilor, coloanelor si descrierii intrarii in stoc se construiesc din ce ramane activ pe overlay, cu denumirile proprii ale sablonului (textul din PDF sau numele dat de utilizator), nu dintr-un nomenclator general; stergerea unui element de pe overlay scoate si etichetele lui.

## Înainte de predare

1. Rulează verificările adecvate și inspectează toate modificările.
2. Actualizează `docs/PROJECT_STATE.md` cu starea efectivă, validările, riscurile și următorul pas.
3. Încheie ciclul cu o descriere completă; scriptul actualizează jurnalul, face commit și predă lui Codex:

   ```powershell
   .\tools\agent-cycle.ps1 finish -Agent claude `
     -Summary "ce s-a schimbat și de ce" `
     -Tests "verificările executate și rezultatul" `
     -CommitMessage "claude: descriere scurtă"
   ```

4. După commit, oprește lucrul. Nu începe următorul task în același ciclu.

## Butoane colorate dupa tipul actiunii si padding (regula permanenta, 08 octombrie 2026)

- Un buton secundar nu mai ramane alb: `class="refresh act-<tip>"` coloreaza dupa actiune: `act-confirm` (verde: salveaza, adauga, preia, seteaza), `act-reload` (albastru: actualizeaza, verifica, testeaza, reincearca), `act-nav` (gri-albastrui: inapoi, spre alta pagina), `act-edit` (galben: editeaza, redenumeste), `act-close` (rosu deschis: inchide, renunta, anuleaza), `act-export` (violet: export, descarca). `primary` (verde plin) ramane pentru actiunea principala, `danger` (rosu plin) pentru stergere.
- Un buton nou de tip `refresh` primeste obligatoriu una dintre aceste clase; iconitele de pe randurile tabelelor raman cele din regula iconitelor.
- Tot ce se pune direct intr-un card `.catalog` (zona de fisier, rand de filtre, text, banner) are padding lateral de 24 px (`.catalog > ...` il da implicit); un text cu fundal colorat (insigna, total) are padding propriu, minim 6 px sus/jos si 12 px lateral.
- Cardurile paginii de produs stau in doua coloane: produsul in stanga, restul (unde sunt bucatile, rezervari, formularul de miscare) unul sub altul in coloana lata.
- Numaratoarea unui set (taburi de categorie, titluri de sectiune, liste) se arata ca insigna `<span class="count-badge">N</span>` (acelasi stil ca numarul din titlul unui card, de exemplu „Registru furnizori 1”), nu in paranteze. Un element urmat de alt element pe acelasi rand (nume + insigna, buton + nota) are spatiu intre ele (min. 8 px).
- Dupa un rand de butoane (`.editor-actions`) urmeaza spatiu (18 px, 28 px inaintea unui titlu): textul explicativ, titlul sau cardul urmator nu stau lipite de butoane. Un comutator (On/Off) este totdeauna `ToggleSwitch`, nu o casuta bifabila simpla.
- Butoanele alaturate au intotdeauna aceeasi inaltime: 40 px (32 px in randuri de tabel), fixata in CSS pentru `primary`, `danger`, `refresh`, `secondary`; un simbol din buton nu il face mai inalt. Orice buton de actiune nou foloseste una dintre aceste clase (plus `act-...` pentru `refresh`), niciodata un `button` fara clasa langa alte butoane.
