# Propunere: actualizarea aplicatiei de pe server din masina de dezvoltare

Scris la 20.10.2026. Fara diacritice. Stare: propunere, nimic implementat.

## Context
- Masina de dezvoltare construieste si verifica aplicatia (Release, `tools\run-checks.ps1`). Serverul (tinta: container / NAS, vezi `SUPERVIZOR_SI_JURNAL.md`) doar o ruleaza.
- Modulele sunt compilate in acelasi assembly (`Routes.razor` foloseste `typeof(Program).Assembly`, `MapRazorComponents<App>()` fara assembly-uri aditionale), deci unitatea de actualizare este aplicatia intreaga, cu repornire. Reincarcarea unui modul la cald nu se face (rute statice, DI inghetat dupa `Build()`, circuite deschise pe cod vechi).
- Exista deja: supervizor cu repornire la exit 75, `/health`, backup verificat al bazei (`DatabaseBackup`), blocaj de mentenanta, jurnal de audit, `AppDataRoot` (datele separate de cod).
- Lipsesc: versiune a aplicatiei, runner de migrari DB (doar `BlazorStoc_create.sql` + `BlazorStoc_upgrade_0.2.sql`), pachet de livrare, schimbul de versiuni pe server, rollback.

## Tinta (decizia utilizatorului, 20.10.2026)
Serverul este o masina Windows (nu container/NAS): supervizorul (`tools\supervisor.ps1`, ulterior serviciu Windows) porneste aplicatia din `current`. Partea de container din versiunile anterioare ale propunerii se elimina. Actualizarea se poate face **din aplicatie** si **manual, prin installer**, chiar daca aplicatia a cazut ireversibil; ambele cai folosesc acelasi Updater (sectiunea 4).

## Principiu
Serverul nu primeste comenzi de la masina de dezvoltare. Dezvoltarea produce un **pachet semnat**; pachetul ajunge pe server (incarcat de administrator sau depus intr-un folder); serverul il verifica, il aplica si se intoarce singur la versiunea veche daca noua nu porneste sanatos.

## 1. Pachetul de actualizare (`tools\release.ps1`, pe masina de dezvoltare)
1. Ruleaza suita completa (`run-checks.ps1`); la esec nu produce pachet.
2. `dotnet publish -c Release` pentru platforma tinta (framework-dependent daca serverul are .NET 9, altfel self-contained).
3. Scrie `manifest.json`: `version` (ex. `0.5.0+20261020.1`), `minFromVersion`, hash SHA-256 pe fiecare fisier, lista migrarilor DB incluse (`0003_...sql` cu checksum), versiunile modulelor (`IModule.Version`), versiunea componentelor externe (worker OCR, modele ONNX/Tesseract) cu hash propriu.
4. Arhiva `BlazorStoc-<versiune>.bsu` (zip) semnata. Algoritm: ECDSA P-256 / SHA-256 (in .NET, fara pachete suplimentare). Cheia se genereaza pe masina care compileaza (`release.ps1 -NewKey`); cheia privata ramane pe acea masina, protejata cu DPAPI pe utilizator, in afara git (`.gitignore`), nu in `local-secrets\` care se comite. Fara semnatura valida de la o cheie de incredere pachetul se refuza (vezi „Cheile de incredere" in sectiunea 7).
5. Rezultatul: `releases\` pe masina de dezvoltare + `releases\CHANGELOG-<versiune>.txt` (generat din `IMPLEMENTED.md`).

## 2. Transportul spre server (decizia utilizatorului, 20.10.2026: doua cai, fara inbox)
- **A. Incarcare din aplicatie** (Setari -> Actualizare, doar administrator): alegi fisierul `.bsu`; pachetul ajunge in `updates\staged`, se verifica si abia apoi se cere confirmarea.
- **B. Installerul manual** (`BlazorStoc-Actualizare-<versiune>.exe`, sectiunea 4), copiat pe server prin orice mijloc.
- Nu exista folder `inbox` si nicio observare automata de fisiere.
- Nu recomand: server care interogheaza un URL public (adauga o dependenta de internet si o suprafata de atac) si acces de la dezvoltare la server cu drept de a porni procese.

## 3. Pe server: cod si date separate
```
/app/releases/<versiune>/     cod publicat, nemodificat dupa dezembarcare
/app/current -> releases/..   pointer (symlink / fisier current.txt pe Windows)
/app/updates/staged           pachete incarcate, despachetate si verificate
/data/...                     AppDataRoot: baza, assets, chei Data Protection, jurnal, backup-uri
```
- Pe Windows: `tools\supervisor.ps1` (sau serviciul Windows care il inlocuieste) porneste din `current`. Pointerul este un fisier `current.txt` (nu symlink: symlink-urile cer drepturi speciale pe Windows), citit de supervizor la fiecare pornire.
- Runtime-ul .NET 9 se instaleaza pe server o data; pachetul declara versiunea necesara. Alternativ pachetul poate fi self-contained (mai mare, fara dependenta de runtime).
- Se verifica sa nu ramana nimic scris in folderul releasului (`keys\`, `local-secrets\`, `logs\`, `data\` sunt azi langa cod: trebuie mutate in `AppDataRoot`/volum inainte de prima livrare).
- Se pastreaza ultimele 3 versiuni pentru rollback; restul se sterg dupa o actualizare reusita.

## 4. Fluxul de aplicare
1. Administratorul vede pachetul, versiunea, schimbarile si ce module se modifica. Introduce motivul (obligatoriu) si confirma.
2. Aplicatia verifica: semnatura, hash-urile, `minFromVersion`, spatiu liber, nicio operatie de mentenanta/backup/preluare inventar in curs (blocajul de mentenanta existent).
3. Despacheteaza in `releases/<versiune>` (nu atinge `current`).
4. Banner pentru utilizatori: „Aplicatia se actualizeaza in 60 s" (mecanismul `ModuleAlertBanner`), apoi blocheaza scrierile.
5. Backup complet verificat al bazei (`DatabaseBackup`, tip „inainte de actualizare", nu se sterge automat).
6. Jurnal de audit: **„Actualizare aplicatie 0.4.2 -> 0.5.0"** cu motiv, utilizator, hash-ul pachetului (actiune specifica, ca la restul jurnalului).
7. Aplicatia porneste **Updater-ul** (proces separat, vezi mai jos) cu `pending-update.json` (versiune tinta, versiune veche, backup, ora) si se inchide.
8. Updater-ul opreste supervizorul si aplicatia, muta `current.txt`, ruleaza migrarile cu versiunea noua (`BlazorStoc.exe --apply-migrations`, proces scurt, fara interfata) si porneste din nou supervizorul.
9. Versiunea noua porneste normal si scrie `update-result.json`.
10. **Poarta de sanatate** (supervizorul/launcher-ul, nu aplicatia): in 120 s `/health` = 200 si niciun modul nu e `Disabled` din cauza pornirii. Succes: se sterge `pending-update.json`, jurnal „Actualizare reusita". Esec: rollback (6).
11. **Rollback automat:** pointerul revine la versiunea veche; daca s-a aplicat vreo migrare ireversibila, se restaureaza backup-ul de la pasul 5 (mecanismul de restaurare existent); jurnal „Actualizare esuata, revenit la 0.4.2: <motiv>"; banner pentru administrator pana la confirmare.

### Updater si installer manual (aplicatia poate fi moarta)
- **Updater** = un executabil mic, separat de aplicatie (`updater\BlazorStoc.Updater.exe`, in afara `releases\`, deci aplicatia nu il inlocuieste in timp ce ruleaza si nici o versiune stricata nu il ia cu ea). Nu foloseste nimic din aplicatie ca sa porneasca. Face toti pasii 3-11: verificare pachet, despachetare, oprire, backup DB, schimb de `current.txt`, migrari, pornire, poarta de sanatate, rollback, jurnal in `logs\updater-<data>.log`. Este singurul loc cu logica de actualizare.
- **Calea din aplicatie:** aplicatia doar valideaza, cere confirmarea si lanseaza Updater-ul (pasul 7).
- **Calea manuala:** pentru fiecare versiune, `release.ps1` produce si `BlazorStoc-Actualizare-<versiune>.exe` (installer auto-extractibil; IExpress este in Windows, iar daca nu ajunge se foloseste un executabil mic scris in .NET). Contine pachetul semnat plus Updater-ul in versiunea lui. Rulat ca administrator pe server, cu aplicatia pornita sau nu: verifica semnatura, opreste ce ruleaza, face acelasi flux si arata progresul intr-o fereastra de consola. Nu cere ca aplicatia sa mearga, nici autentificare in ea; cere doar drept de administrator Windows si acces la baza (contul de migrare din `local-secrets` / configuratia serverului).
- **Aplicatia moarta si fara versiune buna:** installerul poate fi rulat cu `--repair` (reinstaleaza versiunea curenta din pachet), iar cu `--rollback` revine la versiunea anterioara din `releases\` (si, la cerere, restaureaza ultimul backup „inainte de actualizare"). Un installer pentru versiunea X ruleaza si peste o instalare stricata, fiindca nu depinde de continutul lui `current`.
- Semnatura se verifica de Updater cu cheia publica proprie (nu cu cea din aplicatie, care poate fi stricata). Un pachet nesemnat se refuza si manual.
- Installerul scrie in jurnalul de audit al bazei, la prima pornire a aplicatiei, ce actualizare s-a facut (jurnalul de pe disc este sursa cand aplicatia nu merge), cu actiunea „Actualizare aplicatie X -> Y (installer)".

## 5. Migrari DB versionate
- **Implementat in etapa 1 (20.10.2026):** migrarile existau deja ca fisiere SQL incorporate `Assets/Migrations/NNN.sql` (43 acum), rulate de `MariaSchemaMigrator`/`--migrate-schema`; ele raman formatul pasilor (nu se introduc clase C#, ar fi un al doilea mecanism). Ce s-a adaugat: migrarea 43 creeaza `schema_migrations(version, description, checksum, origin, applied_utc, applied_by_version)`; `MariaSchemaLedger` o citeste/scrie cu contul `app`; `MariaSchemaMigrator.Plan` alege ce ruleaza (fara registru sau cu registru gol = toate, inscrise `baseline`; altfel doar ce nu e in registru, inscris `applied`; o coloana lipsa pe care nu o aduce nicio migrare in asteptare = lista intreaga din nou, reparatie); checksum SHA-256 pe fisier (sfarsituri de rand normalizate); un fisier editat dupa aplicare apare ca drift (avertisment in jurnal, cod de iesire 3 la `--migrate-schema`); versiunea aplicatiei `AppVersion` (`<Version>` din csproj) in `/health`, Setari -> Module si in registru.
- Regula din `CLAUDE.md` (fara fisiere SQL de upgrade separate) este respectata: fisierele sunt incorporate in aplicatie. Fiecare migratie nou are cel putin o linie `-- column:` si nu se mai editeaza dupa ce a fost livrata (o schimbare este o migrare noua). Pasii care schimba date (nu structura) raman in cod C# cu contul `app`, ca azi (`NormalizeBeneficiaryKeysAsync`, `LinkTemplateSuppliersAsync`).
- Rulate in ordine, sub blocajul de mentenanta, de **Updater** (`BlazorStoc.exe --migrate-schema`, care exista deja si iese cu 0 = schema la zi, 1 = coloane lipsa, 3 = drift), nu de aplicatia web.
- **Contul de migrare (decizie: cea mai solida varianta):** se foloseste contul dedicat `migrator` care exista deja in `Assets/Data/database-accounts.json` (`ESPGestiuneStoc_migrator`: CREATE, DROP, REFERENCES, INDEX, ALTER, CREATE VIEW, TRIGGER pe schema aplicatiei, `REQUIRE SSL`, host `127.0.0.1`, parola in `migration-account.private.json`). Nu se creeaza cont nou si nu se largesc drepturile lui (nu primeste DML, nu se foloseste `root`):
  - DDL il face `migrator`; pasii care schimba date si inscrierea in `schema_migrations` merg pe conexiunea contului `app` (SELECT/INSERT/UPDATE/DELETE), deci niciun cont nu primeste mai mult decat are azi. Un pas separa explicit partea de DDL de partea de date, iar runner-ul alege conexiunea.
  - Pe server, in productie, parola contului `migrator` nu mai este in configuratia aplicatiei web: fisierul `migration-account.private.json` sta in `AppDataRoot\private\` cu ACL doar pentru Administrators si SYSTEM (Updater-ul ruleaza ca administrator), iar aplicatia web nu il citeste. Verificarea de schema de la pornire (`Program.cs`) ramane doar „verifica si semnaleaza"; migrarea la pornire din dezvoltare ramane cum este azi (`Database:MigratorUser/MigratorPassword`) si se opreste in productie printr-o setare.
  - Daca `--apply-migrations` nu gaseste contul sau parola, Updater-ul se opreste inainte de orice schimbare (nimic aplicat, `current.txt` neatins) si spune ce lipseste; Setari -> Baza de date -> Reseteaza conturile il recreeaza.
  - Backup-ul de dinaintea actualizarii foloseste contul `backup` existent, iar restaurarea la rollback contul `restore`; Updater-ul nu foloseste niciodata contul administrator al serverului MariaDB.
- Regula de scriere „expand / contract": o migrare adauga (coloane, tabele) fara sa stearga; stergerea vine intr-o versiune ulterioara. Asa codul vechi merge pe schema noua si rollback-ul nu cere restaurarea bazei in cazul obisnuit. Orice migrare distructiva se marcheaza `-- irreversible` si forteaza restaurarea la rollback.
- `/health` raporteaza versiunea aplicatiei si ultima migrare.

## 6. Componente externe
- Worker OCR (proces separat), modele ONNX/Tesseract: au hash propriu in manifest; se actualizeaza in acelasi pachet, in `releases/<versiune>/`, deci si se intorc cu rollback-ul.
- MariaDB: nu se actualizeaza prin acest mecanism (se face separat, cu backup si fereastra de mentenanta); pachetul declara doar versiunea minima necesara.
- Imaginea de container / .NET: se schimba rar, manual; manifestul declara runtime-ul necesar si aplicarea se refuza daca serverul are unul mai vechi.

## 7. Securitate
- Permisiune noua `setari-actualizare.apply` rezervata administratorului (ca `setari-module.toggle`); nu se slabeste autentificarea pentru agent.
- **Cheile de incredere:** serverul tine o lista de amprente de chei publice (`AppDataRoot\private\trusted-keys.json`, ACL doar Administrators/SYSTEM), gestionata de Updater, nu de aplicatia web. Cheia de semnare se poate genera pe orice masina de compilare; o masina noua intra in lista in doua feluri: (1) un pachet semnat de o cheie deja de incredere poate contine „adauga cheia K" (semnat, cu amprenta in manifest); (2) installerul manual, rulat de un administrator Windows, afiseaza amprenta cheii necunoscute si cere confirmarea explicita (amprenta se compara cu cea afisata de `release.ps1` pe masina de compilare). Din aplicatie nu se poate adauga o cheie noua. O cheie pierduta sau compromisa se revoca printr-un pachet semnat de alta cheie de incredere sau prin installer. Prima instalare are lista goala: installerul cere confirmarea amprentei.
- Semnatura verificata inainte de orice despachetare; cai din arhiva validate (fara `..`); se executa numai fisierele din manifest.
- Hash-ul pachetului si utilizatorul intra in jurnalul de audit; pachetele aplicate se pastreaza in `updates/applied` cu hash.

## 8. Verificare (grupuri noi in `run-checks.ps1 -Group update`)
Pachet cu hash gresit / semnatura invalida / versiune mai veche se refuza; aplicare reusita pe aplicatie falsa (ca `tests\supervisor\fake-app.ps1`); versiune noua care cade la pornire -> rollback automat; migrare care esueaza la jumatate -> restaurare; actualizare cu backup in curs refuzata; doua actualizari simultane refuzate; ordinea migrarilor; retinerea ultimelor 3 versiuni.

## 9. Etape propuse
